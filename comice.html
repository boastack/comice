Comice

Comice

A GPU interaction engine for images and video.

A small engine that puts images and video on the graphics card and keeps them locked to the page, plus plugins for everything you would want them to do. No dependencies, native scroll and pointer handling built in, and every plugin is a state machine driven by real events, not a timeline of guessed durations. Everything runs on one path, a driver produces a signal, a mapping turns it into a plugin parameter, and the parameter reaches the GPU.

01What Comice is

In plain terms

A web page normally draws an image by handing it to the browser and letting the browser paint it. You get no say over individual pixels.

Comice takes that image or video and puts it on the graphics card instead, as a texture on a flat rectangle that sits exactly where the original element was. Once it is there, a small program runs over every pixel sixty times a second, and that program can react to scrolling, the cursor, a drag, or what is actually in the picture.

That is the whole idea. Everything else is plugins deciding what that per-pixel program does.

A runtime, always on, not a one-time edit

Comice runs on a live site, in a visitor's browser, responding to a person who is scrolling right now. The output is never finished, it is different for every visitor, and it never forgets how it was made because it is remaking it every frame.

The closest honest comparison is Lenis, small, doing one thing, invisible when it works properly. Lenis owns scrolling. Comice owns media.

02Where it stands next to GSAP

In plain terms

GSAP and Motion animate properties, move this to the left, fade that to half opacity, make this number count up. They are excellent at it, and Comice is not trying to replace that.

A property is the whole element at once. Neither can reach inside a picture and change what individual pixels are doing. So no animation library can turn a video into dots, cut a person out of a photo, or make a headline sit behind someone's shoulder. That is not a weakness in GSAP. It is a different machine, working one level deeper.

Works with GSAP, Motion and Lenis removes the only real objection a developer has, must I throw away what I already use.

03State machine, not timeline

In plain terms

Most animation tools think in durations. Play this for 400ms, then that for 600ms. That works for a fixed sequence, but it breaks the moment a real person interrupts it, moves the cursor away mid hover, releases a drag early, scrolls back up before a reveal finished.

Comice plugins are not durations. They are states with rules for moving between them, and the rules are driven by real events rather than a clock. A card does not play a 400ms hover animation, it enters a hovered state and stays there until the pointer actually leaves, however long that takes.

Is this new? Honestly, not the idea itself. XState has done formal state machines for JavaScript for years, and is the standard answer for exactly this class of bug, invalid states caused by interruption. Motion's whole model is declarative and state driven already, describe what a component looks like in a given state and it figures out the transition. Neither claim here is that state machines for UI are new. The actual gap is narrower and more specific, nobody has wired a state machine into a WebGL render pipeline driving raw shader uniforms rather than DOM properties. XState does not render anything. Motion animates CSS and transform, not a texture on the GPU. That is the real, defensible difference, not the state machine idea on its own.
idle→ entering→ active→ leaving→ idle

A generic shape every interactive plugin follows. Each state owns its own easing and duration, and a transition only fires on a real event, pointer enter, drag release, scroll crossing a threshold, never on a timer guessing when the last one probably finished.

Interrupt safe
Leaving mid enter reverses from wherever the animation actually is, not from a hardcoded start point. No snapping, no restart.
Driver agnostic
The same state machine accepts events from scroll, pointer, drag, click or time. A spotlight built for hover works unmodified under a click driver.
Composable
Plugins chained together share one state per element rather than fighting over separate timelines, so a morph and a color grade can both react to the same active state.
Debuggable
A plugin instance always answers what state am I in right now, which a duration based tween cannot honestly answer mid flight.
// Every interactive plugin exposes the same shape
const card = comice('.project').use(spotlight({ peers: '.project' }))

card.state              // 'idle' | 'entering' | 'active' | 'leaving'
card.on('active', () => {})
card.on('leaving', () => {})
card.transition('active')   // force a state, same rules apply
Why it matters here specifically. Most of the interaction bugs in hand built scroll and hover effects come from exactly this gap, a timeline assumes nothing interrupts it, and everything real eventually interrupts it. That problem is well understood for DOM state. It is not well solved for GPU media state, where the thing being interrupted mid transition is a shader uniform, not a CSS property, and existing state libraries have no opinion on that at all.

04Core API and native drivers

What competing with GSAP in its own domain actually requires, a real top level API and its own input handling, with zero dependency on GSAP, ScrollTrigger or anything else to get moving.

Core methods

comice(target)
Wraps one or more elements, returns a chainable instance. Same shape whether target is a CSS selector, an element, or a NodeList.
.use(plugin)
Attaches a plugin, chainable, order matters for the render pass list.
.driver(driver)
Attaches an input source. Any plugin works with any driver without being rewritten.
.set(props)
Applies immediately, no transition, matches gsap.set().
.transition(state, opts)
Forces a state change through the normal interrupt-safe rules, matches gsap.to() but state-based rather than property-based.
.on(event, fn) / .off()
State and lifecycle events, active, leaving, ready, error.
.destroy()
Tears down the plugin chain and releases GPU resources for this instance.

Native drivers, no dependency

Comice does not need ScrollTrigger. It reads native browser scroll-linked animation where available and falls back to a lightweight IntersectionObserver and scroll listener where it is not, entirely inside core.

scroll(opts)
{ threshold, root, offset }. Uses the native ScrollTimeline where the browser supports it, so scroll-linked plugins run on the compositor thread, not the main thread.
pointer(opts)
{ radius, lag }. Raw pointer position and velocity, normalised against the element's bounds.
hover(opts)
{ intent }. Enter and leave with a debounce so fast pass-overs do not fire a full state cycle.
drag(opts)
{ axis, inertia }. Pointer and touch drag with momentum, feeding the same event shape as scroll.
click(opts)
{ toggle }. A single discrete event, useful for state machines with only two states.
time(opts)
{ duration, loop }. The one driver that behaves like a classic tween, for plugins that genuinely want a duration.
// Zero dependencies, this is the whole setup
import { comice, scroll, hover } from 'comice'
import { spotlight } from '@comice/spotlight'

comice('.card').use(spotlight()).driver(hover({ intent: 80 }))
comice('.hero').use(morph({ operation: 'breakout' })).driver(scroll({ threshold: 0.5 }))
The thing that actually makes this compete with GSAP. Not more effects, GSAP has plenty. It is that Comice ships a complete, native, dependency-free input layer of its own. Nobody has to install ScrollTrigger to get scroll-linked media, and on browsers with native ScrollTimeline support the scroll driver never touches the main thread at all.

05What is in and out

In plain terms

The line is not file formats, it is whether media is involved. SVG, text, canvas and the DOM are all legitimate participants, as masks, sources, companions or targets. If a feature still makes sense with no image or video present, it belongs somewhere else, not here.

Not an effect gallery
The catalogue documents what the engine reaches, it is not an inventory owed to anyone.
Not general animation
If it animates something that is not media, GSAP and Motion already do it well.
Not a 3D engine
Flat planes with clever shaders. Meshes, lights and cameras belong to Three.js.
Not AI image generation
Reading an image with ML, depth, subject, colour, is in scope. Rewriting it is a different product.
Not scroll fades
Browsers do scroll linked fades natively now, on the compositor. A JavaScript version would be worse.
Not a video player
No chrome, captions UI, HLS or DRM. Comice takes a video element someone else configured and gives it a GPU surface.

06How it is put together

In plain terms

Comice copies GSAP's shape. GSAP core changes a number over time, ScrollTrigger and SplitText are separate add ons installed only when needed. Comice core puts media on the graphics card and keeps it in the right place, with zero effects included. Every effect is a plugin.

Core
comice, required, under 10 KB

Media on the GPU, the state machine, native drivers, the render loop, mobile budget, fallback contract. Ships with zero effects.

Plugins
@comice/*, opt in

Everything that does something to media. Registered explicitly, tree shaken when unused.

Presets and showcase
not the library

Saved configurations and a gallery site. Built on the public API. Never required.

The five operations everything reduces to

Merge
Many pieces become one. Three panels joining into a single hero.
Breakout
One piece becomes many. A hero splitting into feature cards.
Distribute
Pieces travel into an arrangement. Radial fan, film strip, shelf.
Mask
Media takes the shape of something. Logo, lettering, any SVG path.
Recompose
One layout becomes another. Grid opening into fullscreen.

07The shared GPU primitives

In plain terms

Four things turn up in more than one plugin. A mask. Two images resident at once. The previous frame. Noise and displacement. Each one looks like a feature of whichever plugin needs it first, and each one is actually a capability of the renderer underneath.

If masks get built inside reveal, then morph needs masks and builds its own, then vision needs masks and builds a third, unifying them later means rewriting three plugins. Building them once, in core, before the first plugin needs them costs a design pass. Building them four times costs a rewrite.

This is the one section that has to be right before the GPU pipeline is written, not after. Everything in section 08 is a consumer of these four. A plugin can be replaced later without touching its neighbours. A primitive cannot, because by then every plugin has an opinion about it.
Mask field
One representation, many producers. A mask may come from a shape, text, the cursor, an image, a video, a segmented subject, or a depth threshold, and any plugin can read it. The cursor case is a field sampled in the shader, never DOM clipping, so it costs nothing in layout and stays smooth under load. Consumed by reveal, morph, dissolve, distort and vision.
Multi-texture residency
Two or more sources on the card at once, addressable in the same pass. This is the precondition for every A to B transition, dissolve's whole job, and for particles reassembling into a different image than it scattered from. Already implied by dissolve's "both resident at once", made explicit here because it constrains texture-unit budgeting on mobile.
Temporal feedback
The previous frame, available to the current one. A ping-pong buffer pair allocated once at setup, never per frame. Trails, echo, ghosting, persistence, smear and feedback distortion are all the same capability with different decay and offset. footage's echo is one consumer, not the owner.
Noise and displacement
One GLSL library, simplex and curl noise plus a common displacement sampler. dissolve's noise and liquid transitions and distort's liquid and glass presets are the same math pointed at different targets. Two copies would drift, and the second one would be written by someone reading the first.
The allocation rule applies hardest here. Temporal feedback is the single easiest place in this whole plan to leak textures, because the naive implementation allocates a target every frame and looks correct while doing it. Buffers are allocated at setup, swapped by pointer, and released on destroy, in line with rule 04 and the mobile budget in section 13.

The mask field, in full

Seven producers, one contract. Shape, text, cursor, image, video, subject and depth all end up as a mask, and every consumer, reveal, morph, dissolve, distort, vision, samples them the same way. What differs is how each producer gets there, not what it hands over.

Procedural
Cursor only. A point, a radius, a softness, a falloff curve, held as a tiny uniform block and evaluated analytically inside the shader that samples it. No texture, no render target, no per-frame upload. This is what section 07's original line about the cursor meant by "costs nothing in layout", and it is deliberately kept out of the texture path below rather than folded in for consistency, forcing it through a texture would mean rendering to one every frame just to read it back.
Rasterized
Shape and text. Vector input, an SVG path or a glyph outline, drawn once to an off-screen single-channel render target at plugin setup(). Re-rasterized only when the source path or text actually changes, never per frame.
Derived
Image, video, subject, depth. Already a texture, reduced to one channel by a small fragment pass. Image and video reduce by luminance. Subject passes through, it is already vision's single-channel alpha. Depth compares against a threshold with softness around the edge, owned here as masking work rather than by vision, whose job in section 08 is producing plain textures, never deciding what counts as inside or outside a mask.

Every producer except the cursor lands on the same shape, a single-channel texture in element-local UV space, values 0 to 1. One tagged union, one sampling function, and the branch between the two lives once, in the mask field's own shader chunk, never copied into reveal, morph, dissolve, distort or vision individually. 

// The shape every producer above resolves to
type MaskField =
  | { kind: 'texture', texture: WebGLTexture, uvTransform: mat3 }   // shape, text, image, video, subject, depth
  | { kind: 'analytic-cursor', center: vec2, radius: f32, softness: f32, falloff: Falloff }

// What every consumer calls, the branch lives here and nowhere else
float sampleMask(vec2 uv);
Lifecycle follows the same discipline as the other three primitives. Rasterized masks allocate their render target once at setup, not per frame. Derived masks reuse one shared reduction target per Comice instance, sized against the mobile DPR cap from section 13, and release it on destroy(). Nothing here allocates inside the render loop, the same rule scheduler.ts and the audio driver already hold to.

vision@comice/visionships v0.5

Owns: understanding what is in the media. Produces depth, subject masks and palettes as plain textures every other plugin consumes. Renders nothing itself.

Produces
depthalphanormalspalettesaliencyedges
Options
depthbooleanEstimate a depth map. Default false.
segmentboolean | 'person'Subject separation. Default false.
palettenumberExtract N dominant colours. Default 0.
refine'edges' | 'matte'matte handles hair. Default 'edges'.
sourceMediaImage or video. Video analysis updates over time rather than resolving once.
updateRatenumberAnalyses per second for video. Default 15, decoupled from the render loop.
Example
// Depth and subject, consumed by two other plugins
comice('#portrait')
  .use(vision({ depth: true, segment: 'person', refine: 'matte' }))
  .use(type({ mode: 'behind', target: 'h1' }))

// Video depth, analysed 15x a second, rendered at 60
comice('#reel').use(vision({ depth: true, source: video, updateRate: 15 }))
Real usage: a fashion editorial where the headline sits behind the model, and the background softly blurs while she stays sharp, computed live from one uploaded photo, no manual masking.
Video is a different problem, not a bigger one. Depth inference is far too expensive to run every frame, so analysis and rendering run at different rates, the depth map updates several times a second while the shader consuming it still runs at 60. The map is interpolated between updates rather than stepping visibly. This is an architectural constraint on vision from the first line, not an optimisation added later, because a still-only depth path has to be restructured to accept it.
Excludes

Not image generation, inpainting or style transfer. Vision reads media, it never rewrites it. Never per-frame inference, and never its own rAF loop, the analysis cadence gates inside the shared scheduler.

dissolve@comice/dissolveships v0.3

Owns: moving between two pieces of media that are both resident at once.

Transitions

Options

from / toMediaSources. to may be an array for a sequence.

Example

  transition: 'displace', to: images, map: '/wave.png'
})).driver(scroll())

// Noise drives the threshold, so regions cross at different times
comice('.hero').use(dissolve({
  transition: 'noise', from: imageA, to: imageB,
  noise: { scale: 2, intensity: 1, softness: 0.2 }
}))
Real usage: a case study gallery where each screenshot melts into the next as the visitor scrolls, using a wave shaped displacement map so the edge of the transition ripples instead of cutting straight across.
Why noise matters: a crossfade moves every pixel at the same rate, which is the one thing a real material never does. Noise controls the threshold instead, so parts of the image cross over early and others hold, and liquid adds displacement on top of that so image A appears to flow into B rather than fade. Both read as a material changing state rather than two pictures being mixed.
Excludes

Transitions between pages belong to persist, which also keeps playback alive across the route change. liquid shares distort's displacement sampler rather than carrying its own, see section 07.

Excludes

No model files, no scene graph, no shadows, no physics. A project needing those needs Three, and Comice composes beside it. Parallax is a depth-displaced plane, it is not the beginning of a 3D engine.

09Where this actually stands

Everything above describes what Comice does when it is finished. This is what is built today, so the spec can be read without guessing which parts are real.

LayerStatusDetail
State machineBuiltidle, entering, active, leaving, interrupt safe, rest and display transforms separated.
Shared schedulerBuiltOne rAF loop, visibility gated, crash isolated per callback.
DriversBuiltscroll, hover, pointer, audio. drag, click and time still missing.
Signal and mappingBuiltNamed signals to plugin parameters, clamp, remap, ease, smooth. Fully tested.
GPU pipelineNot builtNo renderer, no texture management, no shaders. Section 07 specifies what it has to carry.
The four primitivesNot builtMask field, multi-texture residency, temporal feedback, noise and displacement.
PluginsNone existAll eighteen in section 08 are specification. The plugin contract has never met a real consumer.
The one thing this ordering depends on. Core's plugin contract, setup, teardown and the params object a mapping writes into, has never been exercised by an actual plugin. The first one built is as much a test of that contract as it is a feature, which is why it should be the cheapest plugin to build, not the most impressive one.
Audio is the exception, it already works. The audio driver reports bass, mid, high, energy, amplitude and spectrum, plus beat, onset and drop events, and the mapping layer already routes any named signal into any plugin parameter. Driving a distortion from the bass needs no audio-specific code inside distort, which is the entire reason the signal layer was built separately from the state machine. Note that beat, onset and drop are discrete events rather than continuous signals, so they arrive through .on() rather than .map().to(). 
// Works today, against plugins that do not exist yet
comice('.hero')
  .use(distort()).use(aura()).use(particles())
  .driver(audio({ source: '#track' }))
  .map('bass').to(distortInstance, 'strength', { output: [0, 0.8] })
  .map('energy').to(auraInstance, 'intensity')
  .map('high').to(colorInstance, 'shift')

10Color, OKLCH by default

In plain terms

A gradient between two saturated colours in ordinary RGB often goes grey or muddy in the middle, because RGB describes screen hardware rather than how eyes perceive colour. OKLCH fixes this by blending through a perceptually uniform space, so the same gradient stays smooth and vivid instead.

This is not a new plugin. It is the default interpolation method wherever a plugin blends between two colours, aura's glow, color's duotone, mosaic's palette fills, dissolve's tonal grade. Full browser support exists now, and CSS itself already recommends OKLCH for gradients and color-mix.

11Dependencies

The target is zero runtime dependencies in core.

In plain terms

Written in TypeScript, compiled down to plain JavaScript for the actual published package. This is a step ahead of both GSAP and Three.js, both are written in JavaScript with type definitions bolted on afterward in a separate file, which is why Three's types are so often a release behind the library itself. Writing Comice in TypeScript from the start means the types can never drift out of sync with the code, they come from the same source, not a translation layer maintained on the side.

WebGL layer
Hand written WebGL2. A full WebGL library fits in 7 KB gzipped, Comice needs less than that.
Render loop and state machine
One shared requestAnimationFrame, visibility gating, per element state. Cannot be delegated, it is where mobile budgets and interrupt safety are enforced.
ONNX Runtime Web
The one permitted dependency, inside vision only. Lazy loaded, never bundled, never in core.
Peer adapters
Optional, for GSAP, Lenis and Motion, so nobody has to change their stack.

12Framework wrappers

In plain terms

Neither GSAP nor Three.js ships a separate React version, a separate Vue version and a separate Svelte version of the actual engine. Both ship one vanilla core, and a small hook per framework that does nothing but call that same core inside the framework's own lifecycle.

@gsap/react's useGSAP() is a thin wrapper around gsap.to(), the same call you would make in plain JavaScript, just triggered inside a useEffect and torn down on unmount. react-three-fiber is the same idea for Three.js, one adapter translating JSX into calls against the one underlying engine. Comice copies this shape exactly, because core is already framework-agnostic vanilla JavaScript with zero dependencies, wrapping it costs almost nothing.

@comice/react
useComice() hook. Instantiates on mount, calls .destroy() on unmount, re-attaches when the selector or options change.
@comice/vue
A composable, useComice(), against Vue's onMounted and onUnmounted.
@comice/svelte
A Svelte action, use:comice, following the same mount and destroy pattern as Svelte's own actions.
// React, the wrapper never touches the plugin API itself
import { useComice } from '@comice/react'
import { spotlight } from '@comice/spotlight'

function ProjectCard() {
  const ref = useComice(c => c.use(spotlight({ peers: '.project' })).driver(hover()))
  return <div ref={ref} className="project"></div>
}
Why this stays out of v0.1. A wrapper is only worth writing once the core API it wraps has stopped changing, writing it earlier means rewriting the wrapper every time a plugin's shape shifts. Framework wrappers belong after the plugin surface is stable, not before.

13Mobile

GSAP is not desktop only, it is JavaScript. The real constraint has always been the GPU and the battery, not the library. Mobile web is required, not optional, it is half the audience on day one.

Cap the pass chain
One or two passes on mobile. Beyond it, merge passes or drop the lowest priority ones.
Scale resolution
Cap device pixel ratio at 1.5 to 2 rather than honouring 3x displays.
Render only when visible
Off screen planes and hidden tabs do zero work.
Watch the frame clock
Step down resolution, then chain length, then a static poster if frames keep missing budget.

14Studio, the visual editor

In plain terms

A visual tool where someone without code uploads a photo or video, picks plugins from a sidebar, tunes them live, and exports something to use elsewhere, the Aminos.app pattern applied to Comice.

The strongest single feature for that tool is exactly the two things Comice already does that nothing else does, vision's depth and subject data, and particles turning any source into a cloud of points. Upload a photo, get particles driven by real depth, tune the motion, export. That is a genuinely strong demo, not a filler feature.

What export actually means here

JSON config is the real export, GIF is a nice extra, not the headline

A GIF is a fixed, baked, non-interactive loop. Comice's actual output is a live WebGL state machine reacting to a real pointer or scroll position, exporting to GIF means throwing that away and shipping something indistinguishable from tools that already exist and are free, ParticleFX Studio already does exactly this.

The export worth building the product around is a small JSON config describing the source, the plugin chain and its options, the same idea as a Lottie file, except the point is not the JSON itself, it is that the library can read that JSON straight back and run the real, interactive thing. GIF export is worth offering as a one click extra for people who just want a shareable clip, but it should never be the thing Studio is sold on. 

// What Studio exports, and what the library consumes, same file both directions
{
  "source": { "type": "image", "src": "upload.jpg" },
  "plugins": [
    { "use": "vision", "depth": true, "segment": "person" },
    { "use": "particles", "mode": "cloud", "count": 80000, "motion": { "noise": 0.3 } }
  ],
  "driver": { "type": "scroll" }
}

// The library runs it directly, no separate player, no separate format
comice('#stage').load('./export.json')

Why it is not part of the plan yet

Same reasoning as the framework wrappers, sequencing, not doubt. Studio hard codes assumptions about the plugin config shape. Built before the plugin options stop moving, it gets rewritten with every change. Built once the eighteen plugins above have shipped and settled, it is a thin form over a format that already works. It belongs after v1.0 in the build order below, not before it, and revenue, if there ever is any, belongs there too rather than on the library itself, in keeping with the licensing decision below.

Native mobile languages, Flutter, Kotlin, Swift

In plain terms

Not a Comice branded app, the library itself running as an interaction layer inside a native mobile app, so a Flutter or Kotlin developer gets the same kind of media response Comice gives a web developer. Checked what this would actually take rather than assuming it is a simple port.

Comice's shader math, the SDF operations in morph, the smin blending, the distortion fields, is portable in principle, GLSL translates reasonably closely to Flutter's shader language and to Android's AGSL, both now run real-time fragment shaders natively. What does not port is the JavaScript half, the state machine, the driver system, the plugin API, none of that runs inside Flutter or a native Android view. A native binding is not a wrapper the way the React or Vue packages are, it means rebuilding the state machine and driver system a second time in Dart or Kotlin, reusing only the shader math underneath. A real, separate engineering project, not something to promise alongside the web library.

Where this sits in the plan. Not in the roadmap below. Worth revisiting once the web library and Studio exist and there is a specific team asking for it, building a second engine on spec before the first one has users would be the same mistake as building Studio too early, just more expensive.

15Licensing

Free and MIT, both the library and the examples

Webflow acquired GSAP and made the whole thing free in 2025, including plugins that used to cost money. The paid plugin model this might have copied was removed from the market by the biggest player in it.

Comice is unknown, GSAP is on eleven million sites and costs nothing. A paid tier now buys friction at exactly the moment adoption matters more than revenue.

16The rules

01
Core earns its size in every project

Nothing enters core unless every user needs it. Target, under 10 KB.

02
Plugins are peers, not favourites

Official plugins use the same public API a stranger would.

03
Presets are data, not code

Anything a preset does, a user can write by hand and change halfway through.

04
Degrade, never disappear

No GPU, reduced motion, weak phone, failed load, the media still shows.

05
The page stays real

Real text, real links, real layout underneath. The canvas mirrors the page, never replaces it.

06
States, not durations

Every interactive plugin is a state machine driven by real events, interrupt safe by construction.

07
Say no in public

A written list of what Comice will never do protects the core from the catalogue.

GLSL, not WebAssembly, for morph and particles

In plain terms

The heavy math in morph and particles, the SDF distance field, the position updates, does not run as JavaScript, it runs as GLSL inside the WebGL shader, on the GPU, already in parallel across every pixel or point at once. There is no JavaScript loop there to replace with WebAssembly, the computation was never in JavaScript to begin with.

WebAssembly genuinely is 10 to 100x faster than JavaScript, but only for self-contained, sequential math with no back and forth to the browser. The moment code crosses the boundary between WASM and JavaScript repeatedly inside a hot loop, that speed gain disappears, and a state machine reading scroll position and DOM bounds every frame is exactly that kind of repeated crossing. Using WASM for morph or particles would mean computing positions on the CPU and uploading them to the GPU each frame, slower than the shader doing it directly, plus a second toolchain, plus a compiled binary working against a 10 KB core budget.

Where WASM is a real candidate, later, narrowly. Only for CPU-bound, sequential work that cannot be a shader, error diffusion dithering inside mosaic is the one plugin in this whole plan that genuinely qualifies, each pixel depends on the one before it, which is the opposite of what a GPU is good at. Worth a small, isolated WASM module there if it ever becomes a bottleneck, never the engine itself, and never morph or particles, which are already running at the speed a CPU path would be trying to reach.
What is deliberately not decided yet. Testing strategy, a shader is not something a unit test catches, the honest answer is visual regression against reference screenshots, but that is worth setting up once morph exists to test, not before. Same for CI and a release process, both are team-scale concerns, and adding them now while building solo would be exactly the kind of premature process this whole plan has been avoiding elsewhere.

18Build order

Ordered by what each step makes safe to build next, not by what would be most exciting to announce. A release bundles whatever is ready, a phase says what unblocks what, and the two are allowed to differ. What is not allowed is building something before the thing it depends on has been proven.

v0.1

Core, then one cheap plugin

State machine, native drivers, plane, sources, pass chain, mobile budget, fallbacks. Then reveal, deliberately the least impressive plugin on the list, because it is CSS and geometry with no shaders, and its only job here is to answer whether .use(), setup(), teardown() and the params object a mapping writes into actually hold up against a real consumer. Getting that answer from the cheapest possible plugin is the entire point. If the contract is wrong, it is wrong now, before seventeen more are built on it.

v0.2

The GPU pipeline and the four primitives

The renderer, plus the mask field, multi-texture residency, temporal feedback, and the noise and displacement library from section 07. Every release after this one consumes them, and a primitive cannot be replaced later the way a plugin can. Then morph, which is the right first shader plugin because the legacy prototype already proves the SDF and liquid-blend math against real footage, so the pipeline is being tested rather than the algorithm. The remaining drivers, drag, click and time, land here too.

v0.3

Dissolve and distort, then the daily plugins

dissolve and distort come first in this release for a specific reason, they are the first real exercise of two primitives everything else leans on, multi-texture residency and the displacement sampler. dissolve ships the noise and liquid transitions, distort the liquid and glass presets, and reveal gains cursor and media masks as the first consumer of the mask field. Then spotlight, color, rail and seed, mechanical once the pipeline is proven.

v0.4

Mosaic, ascii, aura, type, layout, particles

The looks that travel. particles ships the image to particles to image round trip, including A to B, which is where per-particle targets constrain the instance buffer layout. No new primitives, no new risk, which is exactly why this tier sits here rather than earlier.

v0.5

Vision, then spatial

The hardest release and the one worth slowing down for, the only plugin with an ML dependency and the only lazy-loaded runtime. Video depth, source and updateRate, is in vision from the first line rather than retrofitted. spatial follows vision rather than accompanying it, because depth has one producer and several consumers, and building parallax against an unstable depth output means building it twice.

v1.0

Footage and persist, then framework wrappers

Chroma key, audio reactive, motion transfer, scrub safe seeking, and media that survives navigation. The family that makes the name honest, a media library rather than an image library. echo, trails and ghosting are written against the shared feedback buffer from v0.2, so there is never a private implementation to refactor away. React, Vue and Svelte wrappers follow immediately after, once the plugin surface stops moving.

v1.5

Studio

The visual editor, built only once the config shape above has proven stable in real use. Upload, depth, particles, export JSON that the library reads back and runs live, GIF export as a secondary option.

The discipline that keeps this a library. Every release ships capabilities, and demos follow from them. The moment a release is planned around what would look good in a gallery, the drift has started. The catalogue serves the engine, never the other way round.
The one ordering rule worth stating outright. Twice in this plan a cheap thing goes before an impressive one, reveal before morph and vision before spatial, and both times for the same reason. The first plugin tests the contract, so it should be the one whose failure is cheapest to diagnose. A producer ships before its consumers, so the consumer is not built twice. Every other ordering question in this document resolves to one of those two.
